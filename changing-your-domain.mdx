---
title: "Changing your domain"
description: "How to move your plugin to a new custom domain without breaking existing installs."
---

When you change your plugin's custom domain, Plugpass moves your pages to the new one and stops serving the old one. Anything still pointing at the old address stops working unless you set it up to redirect.

## Redirect the old domain

As with any site that moves, a redirect keeps search results, shared links and bookmarks working.

Your plugin's signup and login links are baked into each installed copy. Until users update to a version you published after the move, those links point at your old domain.

<Steps>
  <Step title="Send every path to the same path">
    A permanent redirect (`301`) from the old hostname to the new one, mapping every path to the same path. Not just the homepage.
  </Step>

  <Step title="Keep the query string">
    The signup links carry parameters, like `/signup?feature=…&connect=web&platform=anthropic`. Drop them and users who sign up are never told how to connect your plugin.
  </Step>
</Steps>

### How

You do not need a server for this. Most DNS and hosting providers can do it for you.

**Cloudflare**

Point the old hostname at a proxied placeholder record. Add a Redirect Rule for it that targets your new domain with the path appended, and turn on **Preserve query string**.

**Netlify**

Add a rule to your `_redirects` file, such as `/* https://new.example.com/:splat 301!`.

**Vercel**

Add a redirect to your `vercel.json`.

```json
{
  "redirects": [
    { "source": "/:path*", "destination": "https://new.example.com/:path*", "statusCode": 301 }
  ]
}
```

**nginx**

If you already run one, this keeps both the path and the query string.

```nginx
server {
  server_name old.example.com;
  return 301 https://new.example.com$request_uri;
}
```

<Warning>
  **Registrar "domain forwarding" often is not enough.** Many implementations send every request to the homepage, and many drop the query string. Both look like the redirect is working.
</Warning>

### Check that the redirect works

Test with an old signup URL that still has its parameters.

```
https://old.example.com/signup?feature=test&connect=web&platform=anthropic
```

You should land on `https://new.example.com/signup` with `feature`, `connect` and `platform` all still in the address bar. If the path or the parameters are gone, the redirect is not configured the way the links need.

## Implement required plugin changes

Changing your domain or moving your MCP server requires implementation of the monetization code in your plugin & MCP server. Run `/plugpass-implement-code-changes` in Claude Code or `$plugpass-implement-code-changes` in Codex, then publish and release the updated plugin.

New installs will carry the new address, and existing outdated installs will keep working through the old address until they get the new version.

## If Plugpass hosts your MCP server

If your plugin offers MCP tools of its own, you run your own MCP server, and the two steps above are all a domain change needs. If that server is moving to a new URL too, see [If you move your own MCP server](#if-you-move-your-own-mcp-server).

If the only tool your plugin exposes is the access check (`yourplugin_check_access`), Plugpass hosts your MCP server and the rest of this section applies.

### Carve the MCP paths out of the redirect

Your connector URL, `https://yourdomain.com/mcp`, moves with your domain, and installed copies keep calling the old one. Proxy these two paths to your new domain instead of redirecting them.

```
/mcp
/.well-known/oauth-protected-resource/mcp
```

Everything else keeps the redirect from the first section.

Your proxy must connect to the new domain under the new domain's name, pass the `Authorization` header through, and send your old domain in an `X-Forwarded-Host` header.

<Warning>
  **Do not redirect `/mcp`.** Installed copies refuse the connection after a redirect, even though the redirect looks like it worked.
</Warning>

**Cloudflare**

One Worker on the old domain can do both jobs. Remove the Redirect Rule, create a Worker with this code, and add a route for `old.example.com/*` to it.

```js
export default {
  async fetch(request) {
    const url = new URL(request.url);
    const target = `https://new.example.com${url.pathname}${url.search}`;
    if (url.pathname === '/mcp' || url.pathname === '/.well-known/oauth-protected-resource/mcp') {
      const proxied = new Request(target, request);
      proxied.headers.set('X-Forwarded-Host', url.host);
      return fetch(proxied);
    }
    return Response.redirect(target, 301);
  },
};
```

**nginx**

Any other proxy that can route by path works the same way.

```nginx
server {
  server_name old.example.com;

  location = /mcp {
    proxy_pass https://new.example.com;
    proxy_ssl_server_name on;
    proxy_set_header Authorization $http_authorization;
    proxy_set_header X-Forwarded-Host $host;
  }

  location = /.well-known/oauth-protected-resource/mcp {
    proxy_pass https://new.example.com;
    proxy_ssl_server_name on;
    proxy_set_header Authorization $http_authorization;
    proxy_set_header X-Forwarded-Host $host;
  }

  location / {
    return 301 https://new.example.com$request_uri;
  }
}
```

### Check it against your live plugin

Use a premium feature from a copy that is already installed and connected. If it runs, the proxy is working.

### Retiring the old address for good

Keep this setup in place while outdated installs are still in use.

To give it up, remove the domain on the **Domains** page in your publisher settings. Anyone still calling it loses access, so do this last.

<Warning>
  Keep the domain registered while you still want it working. If you let it lapse and someone else acquires it, the tokens your users send to that address go to them.
</Warning>

## If you move your own MCP server

This applies when an MCP server you run moves to a new URL, whether or not your domain changes.

Installed copies keep calling the old URL until users update to a version you released after the move, so keep something answering there.

### Keep the old server running

The simplest way is to leave it up. Don't take the old server down when the new one goes live.

### Or point the old address at the new server

One deployment can answer both addresses. First deploy the new server with the code from your latest `plugpass-implement-code-changes` run.

Then serve the old hostname from the same deployment, such as a second custom domain on your host, or proxy it to the new server. A proxy must connect to the new server under the new server's name, pass the `Authorization` header through, and send your old hostname in an `X-Forwarded-Host` header.

<Warning>
  **Do not redirect your old MCP URL.** Installed copies refuse the connection after a redirect.
</Warning>

**Cloudflare**

Create a Worker with this code and add a route for `mcp.old-example.com/*` to it. The old hostname's DNS record must be proxied through Cloudflare for the route to receive its traffic.

```js
export default {
  async fetch(request) {
    const url = new URL(request.url);
    const proxied = new Request(`https://mcp.new-example.com${url.pathname}${url.search}`, request);
    proxied.headers.set('X-Forwarded-Host', url.host);
    return fetch(proxied);
  },
};
```

**nginx**

```nginx
server {
  server_name mcp.old-example.com;

  location / {
    proxy_pass https://mcp.new-example.com;
    proxy_ssl_server_name on;
    proxy_set_header Authorization $http_authorization;
    proxy_set_header X-Forwarded-Host $host;
  }
}
```

### Check the old address

From a copy installed before the move, use a premium feature. If it runs, the old address is working.

### Retiring the old URL for good

Keep the old address answering while outdated installs are still in use.

To give it up, remove its domain on the **Domains** page in your publisher settings. Anyone still calling it loses access, so do this last.

## If your plugin is in the ChatGPT Plugin Directory

A ChatGPT listing connects to the MCP server address your plugin had when you submitted it. That address can't change. OpenAI treats a plugin at a new address as a new plugin, with its own submission and review.

- **A listing made on your plugin's Plugpass subdomain** keeps working when you add or change a custom domain.
- **A listing made on your custom domain** stops working when you replace or remove that domain. To keep it, keep the old address answering with the proxy in [Carve the MCP paths out of the redirect](#carve-the-mcp-paths-out-of-the-redirect), or submit your plugin to OpenAI again as a new plugin.
- **A listing made on your own MCP server** stops working when you move that server to a new URL. To keep it, keep the old address answering as [If you move your own MCP server](#if-you-move-your-own-mcp-server) describes, or submit your plugin to OpenAI again as a new plugin.
- **Moving the access check to another of your MCP servers** keeps your listing working as long as the old server keeps running. To move your ChatGPT users to the new server, submit a new plugin to OpenAI that uses it. If the new server is on the same domain as the old one, a new version of your plugin can use it instead.
