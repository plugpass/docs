---
title: "Your own MCP server"
description: "How a plugin's own MCP server enforces access: the canonical path that turns on when you publish, and the test path your test users use."
---

When your plugin runs its own MCP server, the `plugpass-implement-code-changes` skill writes the access layer into the server's source: it validates the login tokens Plugpass issues, asks Plugpass whether a user may use a premium feature, and answers with the paywall when they may not. That layer serves two paths.

## The canonical path

Your server's registered URL, usually ending in `/mcp`, is what real users connect to. It enforces access only once your plugin is **published**:

- **Before your first publish**, the canonical path behaves as your server did before Plugpass. Nobody is asked to sign in, no premium check runs, and every tool works for anyone. You can deploy the implemented code at any time without changing anything for the users you have today.
- **After you publish**, the canonical path asks users to sign in and enforces your plans. Enforcement begins within five minutes of publishing.

The server learns whether the plugin is published from Plugpass and keeps the answer for five minutes. Publishing is the only thing that turns enforcement on; deploying never does. If the server cannot reach Plugpass when it starts, it enforces until it can, so an outage never opens a published server.

## The test path

The same server at its URL plus `/test` (for example `https://mcp.example.com/mcp/test`) always asks users to sign in, from the first deploy, and only your [test users](/test-users) can sign in to it. It runs the same tools and the same access checks as the canonical path, against your current draft, so what you test is the code you will ship.

The `plugpass-test-plugin` skill installs a test version of your plugin that points at the test path. On Claude, where a connector is added by URL, the connect page shows the test path to a test user on the draft. Add it as a connector, turn the real connector off while you test since the two carry the same tool names, and remove the test connector when you are done. On ChatGPT, the test plugin reaches the test path through an app you create in developer mode, as [Testing on ChatGPT](/test-users#testing-on-chatgpt) describes.

## When Plugpass's signing keys can't be fetched

Your server checks every login token against Plugpass's public signing keys, which it fetches and keeps for a few hours. If it can't fetch them, it answers `503` with `Retry-After` instead of asking the user to sign in again, so a brief outage never makes an AI product show your users as signed out. The `plugpass-implement-code-changes` skill adds this to your server on its next run.

## What a tool call uses

A paid tool's call uses up its allowance only when the tool succeeds. When a call throws or returns an error, the access layer gives back what the call took, so your users never pay for a call that failed.

A tool can also be limited by the things it handles instead of its uses, like the leads it returns or the leads it's sent. Sync finds these counts in your server's code and names each one. Your Plans page then offers them as limits and credit costs, and once you pick one, you can rename it on your Features page. On its next run, the `plugpass-implement-code-changes` skill wires your tool to report each count on every call. When a user has fewer left than a call finds, the result is trimmed to what they have left, with a note saying what was held back and how to get the rest.

## Deploy, then test, then publish

Deploy your server before you publish. Deploying doesn't ask your users to sign in or turn on limits or paywalls until you publish, so deploy whenever you like and test against the test path in the meantime.

Push or merge your plugin's own changes after you publish, so users receive them with your plans already live. Your first publish is the exception. It starts requiring users to sign in and enforcing your plans on every installed version of your plugin at once, so push or merge the plugin first. If your plugin is listed in the Claude Plugin Directory or the ChatGPT Plugin Directory, publish the new version there too, since a directory only delivers a version it has published. If your plugin already has users, wait about a day before you publish so most users will have updated to the plugin version that properly handles your premium feature access checks. The publish page lays out the steps in order for each publish.
